The 27 gaps, by what the user loses

  1. Losing a phone is not recoverable through the app — KeyRecovery is built and tested on-chain; engine, backend and app cannot file, veto or execute a rotation (WP §10.3 promises it).
  2. Vault safety limits are unreachable — daily limit, pending-window cancel, withdraw-to-key exist on-chain only (WP §10.5).
  3. Disputes can be raised but never resolved — the arbiter path (propose split → approve → execute → escrow.resolve) is unwired; a disputed trade stays locked.
  4. Nobody triggers timeouts — autoSettle / refundOnTimeout / cancelRaise / markDefaulted are permissionless but no keeper calls them.
  5. Sellers cannot manage listings — no price edit, pause, or challenge from the app.
  6. Attestations are invisible — profiles cannot show who vouched under which schema; a false claim cannot be challenged.
  7. Chain-direct detail views — agreement/pool/listing served from the DB mirror; the audit page should diff them against the chain.

Plan, in order: keeper → recovery → vault controls → disputes → listings → attestations → a separate ops CLI for the 64 governance/namespace/treasury functions. Full table and slice plan in docs/26_ENGINE_ARCHITECTURE.md.

What is built vs what is planned on this layer

BUILT — 1,184 lines, used by the reference backend

  • Engine::connect(rpc, key, ParamStore) — one address bootstraps everything; every other contract resolves on-chain through keys::param_key(name)
  • Typed bindings (alloy sol!) for ParamStore, ActorRegistry, SchemaRegistry, AttestationRegistry, ListingRegistry, AgreementEscrow, FundingPools, NamespaceRegistry, CommunityGroups, UserVault — functions and the events the indexer decodes
  • 27 mutating calls (register actor, attest, create listing, commit / commitFromVault / commitNegotiated, settle, dispute, refund, open/contribute/disburse/claim pool, vault deposit, group create/join/contribute/propose/vote/execute, meetings…) each serialized behind send_lock
  • Nonce discipline: fetch-fresh nonces, .call() simulation before every send, one provider per key — the class of "queued-gap" wedges is gone
  • Indexer: cursor-based sync(), joins ListingCreated + AgreementCommitted + SettlementSplit into sales books; reputation_of, stats_for_cells (per-territory median prices); rebuilds from block 0 after any restart
  • Namespace directory, vault balance/nonce/digest helpers, escrow offer nonces

PLANNED — next engine iteration

  • Event streams: start_event_listener() → typed stream so backends push notifications the moment a state changes
  • Micro-trade batching: below microTradeMax, settle off-chain and batch on-chain — free small trades that still build history
  • FFI bindings (Node via napi, Python via PyO3) so any team's backend can use the engine without Rust
  • Multi-chain targets: chain id read at boot; Celo Sepolia → mainnet; address refresh when governance points a ParamStore key elsewhere (UUPS-aware)
  • Per-namespace rate limiting and a delegate-key model in the client (capability subsets)
  • Pinning helper for the data-availability rule (evidence, rationales, canonical listings)
  • Crate rename once the protocol is named; publish to crates.io with the audit

For the app team — the shapes a UI will consume

1. The intent envelope (how a phone authorises anything)

Every mutating action is a small JSON the phone signs with its device key. The backend verifies the signature against ActorRegistry.keyOf(actorId) and only then calls the engine. The UI's job: show the plain-language summary of exactly what is being signed, then sign.

{
  "action":   "Buy",                    // Buy · Settle · CreateListing · JoinGroup · …
  "actorId":  "0x…32 bytes",
  "paramsHash": keccak(stableJSON(params)),
  "nonce":    7,                        // per actor, from GET /nonce
  "expiresAt": 1788735486,              // ~15 minutes
  "signature": secp256k1 over
    "protocol-intent-v1|action|actorId|paramsHash|nonce|expiresAt"
}

2. The vault pay digest (how money leaves a vault)

payDigest = keccak(abi.encode("vault-pay-v1", chainId, vault, actorId, to, amount, nonce))
// the phone signs THIS; UserVault.pay recovers the signer and checks it == keyOf(actorId)
// the backend relays the signature — it cannot produce one

4. Rules a standard UI must keep

  • Never show a status the chain does not have — render the enum, not a guess
  • Money moments show the split (fee · skim · net) exactly as SettlementSplit emitted it
  • An attestation is "who said what, under which schema" — never a bare checkmark
  • Location is a coarse cell or a named place; a street address never appears
  • Rules before money: terms text before a join button, quorum % on every group transfer
  • Anything that moves money has a plain-language confirm sheet and one signature
